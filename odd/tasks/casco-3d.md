# Feature: casco-3d

## Objective
From a vessel's inspections page, the user opens a 3D view of a schematic hull that is generated by code
from the vessel's measurements and split into the 23 standard sections. Each zone is coloured by its
worst finding in the selected inspection (the latest by default). Selecting a zone lets the user
consult that inspection, edit it (photos of that zone) or start a new one. It is a clickable reference,
not a realistic render, and it shows no photos on the model.

## Problem / Why
Today sections are only a list or a grid of buttons (`MapaZonas`), so nobody sees *where* on the hull
the findings are. User request (2026-11-18): "the same app, but in 3D". The view is an extra entry
point, not a top-bar item.

## Decisions

### Scope of Nautic
- Nautic targets naval (warship) hulls first and also other medium and large steel hulls. Multihulls
  are out of scope. `AGENTS.md:9` is reworded in T1.

### Navigation
| What | Decision |
|---|---|
| Entry | "Vista 3D" button in the header of `/inspecciones/buque/:id` (`ListaInspeccionesPage.tsx:135`, next to "Nueva inspección"). |
| Route | `/inspecciones/buque/:id/casco?inspeccion=<id>&zona=<seccionId>`. This is a separate page, not a switch. Both params are optional and are kept in the URL, so "back" restores the view. |
| Inspection shown | The most recent one by default. A selector over the existing paged search (`buscar({buqueId}, cursor)`, 24 per page, no total) offers "Cargar más". If `?inspeccion=` is not in the loaded pages, the selector still shows it. |
| Zone actions | **Consultar** → `/inspecciones/:id/resultados?zona=<seccionId>`. **Editar** → `/vision/:id?zona=<seccionId>`, enabled only with `misPermisos.subirFotos`. **Nueva inspección** → `/vision?buque=<id>&zona=<seccionId>`, always enabled: any signed-in user may create one. |
| Inspection state | There is no "closed" inspection in the model. The actions above are gated by `misPermisos` only, as in the rest of the app. |
| Transition | The vessel name morphs into the page title (`transicionNombreBuque`). A silhouette of the hull shows while three.js loads. Once the scene is ready, the camera flies in and the zones fade in to their colours. With `prefers-reduced-motion`, nothing animates. |

### Colour rule (same as the PDF report)
- Use the photos of the selected inspection in the section (key: `seccion.id`).
- Only analyzed photos (`completada`) are read.
- A finding is a detection that is not a known component and was not discarded. This is the same rule
  as `reporte._hallazgos` + `reporte.py:150-161`.

| Zone state | When | Colour |
|---|---|---|
| `critical` … `low` | Worst taxonomy severity among the findings | Existing severity tokens |
| Hallazgo sin clasificar | There are findings, but none has a known severity (unknown class) | New neutral token (never hidden) |
| Sin hallazgos | Has analyzed photos and no findings | New neutral token |
| Sin analizar | Has photos, none analyzed (pending, in progress or error) | New neutral token |
| Sin fotos | No photos of this section in the inspection | New neutral token |

The neutral states get new tokens in `src/index.css` (light and dark). The canvas reads the computed
token values, so it follows the theme.

### Backend contract change (only one)
Each detection in the photo dict and in the `foto-updated` SSE event gains `descartada: bool`, built in
`resumen_detecciones` (`backend/vision/models.py:353-356`). Nothing else changes: the per-section summary
is computed in the frontend from the inspection detail, which already returns each photo's full
section (`{id, codigo, …}`). No new endpoint.

### Hull geometry
- **Generated by code, no 3D files.**
  - Pure domain functions ported from the prototype (`casco-3d-prototipo.html`, three r147):
    `semimanga`, `fondo`, `cubierta`, `plenitud`.
  - Hull frames go from stern (t=0) to bow (t=1). Strip boundaries fall exactly on zone boundaries.
- **Parameters come in an `Arquetipo` object**, so a future type catalogue only adds data. There is a
  single archetype for now: a **generic steel warship (frigate or patrol vessel)**.
- **Measurements** come from the technical sheet (`eslora_total_m`, `manga_moldeada_m`, `puntal_m`,
  `calado_diseno_m`). Missing or inconsistent values fall back to the archetype ratios:
  - a value ≤ 0;
  - T ≥ D;
  - B ≥ L/2.

| Parameter | Prototype (offshore supply) | Warship archetype (starting values) |
|---|---|---|
| Default ratios B/L · D/B · T/D | 0.21 · 0.42 · 0.81 | 0.13 · 0.62 · 0.45 |
| Default length when unknown | 90 m | 120 m |
| Fullness (aft → mid → bow) | 3.2 → 5 → 2.2 | 2.6 → 3.2 → 1.4 (V bottom, sharp bow) |
| Transom width (× half-beam) | 0.82 | 0.75 |
| Deck rise at the stem | 1.16 D | 1.12 D |
| Superstructure (decorative, not clickable) | Forward house, t 0.64–0.84 | Central block, t ≈ 0.35–0.65, plus bridge, mast and funnel |
| Propulsion (zone `PROP`) | 1 shaft, 1 rudder | 2 shafts with brackets, 2 rudders |
| Sea chests (zone `SEA-CHEST`) | 2 grilles at t 0.44 | Same |

The starting values are tuned by eye during T4. Tests check invariants, not these numbers.

### Zones
- **Standard sections:** the 23 sections of `SECCIONES_ESTANDAR`, with codes like `FWD-BTM`, `MID-BLG-P`,
  `AFT-SS-S`, `FWD-DK`, `KEEL`, `WL-P`, `WL-S`, `PROP` and `SEA-CHEST`. The prototype's banding is kept:
  - **Lengthwise:** thirds by t.
  - **Vertical:** bottom / bilge / side / waterline / deck edge, by height along the frame.
  - **Keel:** `KEEL` is a narrow strip on the centreline.
- **Matching:** a vessel's section is placed on the hull when its `codigo` **exactly** matches a standard
  code. Data stays keyed by `seccion.id`.
  - Sections that match nothing are listed under "Secciones sin ubicación en el casco", next to the
    3D view, and work the same way there. Examples: `SEC-01`, free text, lower case.
  - There is no `es_estandar` field in the model, so matching by code is the only way.
- **Accessible list:** a list of all the vessel's sections with their state is the accessible path, and
  the one page tests use. Selecting a zone in the list or on the hull selects it in both.
- **Photo badge:** zones with photos show a floating badge with the number of photos (any state).

### Technical
- **Stack:** `three`, `@react-three/fiber` and `@react-three/drei` (React 19-compatible versions,
  pinned when installed) plus `@types/three`.
- **Lazy loading:** the canvas is `React.lazy`-loaded on this page only. This is the first lazy chunk in
  the app; three.js must not end up in the entry chunk.
- **jsdom has no WebGL.** Geometry, zone mapping, summary and states are pure functions tested with
  Vitest. Page tests replace the canvas with a test double.
- **Not touched:** `nautic_core`.

## Out of scope
- A vessel type catalogue and more archetypes. `Arquetipo` is ready for them as data.
- A 3D preview in the vessel create/edit forms.
- Uploading a ship's own 3D file (`.glb`): phase 2, with automatic zone assignment plus user
  confirmation.
- Replacing `MapaZonas` with the 3D view. The domain modules must make it possible later without
  duplicating logic.
- `ResultadosPage` still shows the stored `foto.severidad`, so it can differ from the 3D view after a
  discard. Aligning it is a follow-up.
- Live refresh after discarding in the report. A report `PATCH` emits no SSE, so the view updates on
  the next load.
- Multihulls, realistic rendering, photos on the model, editing sections.
